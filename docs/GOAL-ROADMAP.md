# FLS APP 全量原生前端路线

## 最终目标

在 Flutter APP 内实现完整、可日常使用的 FLS 前端，覆盖远程面板和本机面板的业务能力。最终用户不必打开 FLS Web 页面；APP 应以原生页面展示、操作并管理任务、脚本、日志、配置及其他 FLS 功能。它不是只优化在线脚本或版本管理页面，也不是把 Web 页面包进 APP 后换一层样式。

原生 APP 需要从现有 FLS 服务读取和修改真实数据，不能以本地假数据或平行数据模型替代后端。远程和本机连接要复用同一套领域模型与页面操作；本机模式可以使用已有容器/MethodChannel 边界，但业务请求仍应经由 FLS 服务 API。WebView 暂时保留为过渡期的完整能力入口和故障回退，不作为最终主界面。

## 分支与合并策略

APP 与 FLS 后端均在各自 `develop` 分支持续开发；`main` 仅作为当前稳定版本，不直接承载本次原生前端改造。APP 全量原生页面、所需 FLS API、自动化测试和用户验收准备全部完成之前，不把任一仓库的开发分支合并进 `main`，避免用户更新到仅完成一半的前后端组合。FLS 开发版本只用于隔离的测试面板/screen，不替换稳定服务。

## 建设原则

- **先盘点真实产品面，再动导航。** 以当前 FLS Web 前端的页面、表单、操作、角色/状态及使用流程为行为基线；检查后端路由和请求/响应结构，区分页面展示 API、写入 API、长任务/流式日志和 Web 专属能力。
- **确认后端契约，不臆造 API。** 每个原生功能明确现有可用 API、认证方式、字段校验、错误格式、分页/过滤、权限语义和副作用。若缺少契约，先在 FLS 后端及其路由实现中补齐最小稳定 API，再做 APP 客户端。
- **共享连接、分离呈现。** 远程连接通过配置的 HTTPS/LAN 面板地址访问；本机连接访问本机 FLS 服务。页面和领域逻辑共用，不复制出远程版与本机版两套业务实现。不能为方便渲染而把远程面板账号密码转发至 APP 自建中间服务。
- **逐域迁移，保持随时可用。** 原生页面达到每个功能域的读取、主要写操作、错误/加载/空状态与权限要求后，才把该域设为 APP 默认入口。未迁移域继续由 WebView 承接，并始终保留用户主动打开 Web 面板的入口。
- **安全和一致性优先。** 危险操作二次确认；凭据不进入日志；破坏性写操作提示影响并尊重后端校验；长任务可见状态、可取消时提供取消，刷新后从服务端恢复实际状态。
- **可访问且适合移动端。** 以紧凑原生单栏为主，覆盖窄屏、大字、横屏和键盘/读屏语义；宽屏可提供列表与详情双栏。不能照搬桌面 Web 的宽表格、密集导航或把页面截图当成原生视图。

## 分阶段 Goal

### Goal 0：盘点全量功能与 API 契约

输出可跟踪的功能矩阵，至少包含 FLS Web 当前全部一级/二级页面、关键用户流程、读写 API、字段模型、权限/认证、长任务、危险操作、错误状态、APP 迁移状态和对应验收证据。用真实路由/API、模板内表单/JS 请求与测试面板行为交叉核对，避免仅凭 README 或路由名推断功能覆盖面。每个功能标明契约状态：现有 JSON API 可直接复用、现有接口需调整/补强、仅有 Web 表单需新增 API、APP 不适用/保留 Web 并说明理由。

FLS 路由静态初查覆盖以下业务（基于 `$HOME/fls` 的 `develop`，精确提交见上表；Goal 0 仍需继续核对模板、JS、数据结构与权限）：

- 登录、邮箱验证、首次设置和退出：`fls_manager/routes/auth_routes.py`。
- Dashboard、状态、调度器与历史：`dashboard.py`、`status.py`、`api.py`；含 scheduler jobs/status/reload 和 task action/bulk action 等 API。
- 任务、集合、任务配置、运行/停止、日志：`routes/tasks/`、`api.py`；其中表单读写与 JSON API 并存。
- 本机脚本文件、拉取/导入/改名/删除、调试：`routes/scripts/`；不能等同于 APP 已有的在线脚本市场页面。
- 在线脚本源、文档、安装/刷新/任务导入关联、状态、历史、日志、取消/恢复：`routes/online_scripts/`；已有多组 API 和长任务状态接口，需逐操作核对字段与生命周期。
- 系统/任务日志和文件、分组删除：`routes/logs/`、`routes/tasks/logs.py`。
- 依赖安装/重试/取消/历史，以及 Python/Node 等运行时：`deps.py`、`runtime.py`。
- 环境变量和应用配置：`routes/env/`、`routes/config/`。
- 代理配置、测试、质量检查、诊断：`routes/proxy/`。
- 通知渠道、发送测试、投递历史和重试：`routes/notify/`。
- 备份列表、创建/取消/删除、导入/恢复状态和恢复历史：`routes/backup/`。
- 面板状态、版本信息/更新、面板控制、任务日志、时间同步：`routes/about/`、`status.py`。

以上文件路径均相对于 FLS 仓库。该初查未覆盖逐页面行为、所有请求参数、运行中状态或接口安全校验，不能视为已完成的功能/API 矩阵。

**验收：** [FLS-FEATURE-MATRIX.md](FLS-FEATURE-MATRIX.md) 第一轮已完成路由/接口盘点；Goal 0 后续须逐页追踪表单、内嵌 JS 请求与测试实例行为，补全字段/认证/错误契约。明确哪些 API 已可给 APP 使用、哪些需要 FLS `develop` 后端开发；每个迁移域有 APP 页面入口、流程和测试计划。API 新增/变更同时由 FLS `develop` 的后端测试覆盖。

### Goal 1：建立原生前端基础设施

确定远程/本机服务器选择与会话上下文；建立 HTTP/API 客户端、请求超时/取消、统一错误与认证失效处理、结构化领域模型、分页、空/加载/失败状态、刷新策略。为具备相同 API 契约的远程与本机面板提供可替换的数据源；支持测试注入，避免 Widget 直接拼 HTTP 请求。

同时定导航 IA 和基础组件：面板上下文、主导航、任务/脚本/日志等业务入口、可复用筛选/表单/状态、破坏性操作确认、深链返回和当前服务器标识。保留 WebView 入口和现有 LocalSetup 的容器维护职责，业务原生界面不与“安装/运行容器”混成一页。

**验收：** 使用假 API 和契约测试覆盖成功、超时、断网、401/403、4xx 校验错误、5xx、取消与切换服务器；证明请求不会错发到上一个面板；不启动本机面板也不影响远程服务连接。

### Goal 2：迁移核心读操作与任务工作流

优先做日常主路径：任务列表/搜索筛选、任务详情、运行状态与历史、开始/停止/重试等现有 FLS 已支持的操作；任务表单创建/编辑按实际 API 和 Web 语义逐项覆盖。与脚本引用、定时设置及后端校验的关系必须按真实实现明确，不复制 Web UI 字段却忽略其服务端规则。

**验收：** 从 APP 对真实测试面板完成读取和至少一条完整创建/编辑/执行/停止路径；状态变化来自服务端；错误、空结果和加载刷新有自动化测试。迁移前对照功能矩阵逐项核对 Web 的主要用户操作。

### Goal 3：迁移脚本和长任务原生操作

保留现有 APP 本机容器脚本原生目录和安装能力。另行迁移 FLS 面板的在线脚本、服务端脚本文件、拉取/导入、调试、关联任务及运行日志，统一通过 FLS 后端 API，不直接访问面板脚本存储；本机一次性依赖安装仍遵守现有容器命令和取消/回滚边界。

**验收：** APP 覆盖对应 Web 域中全部确认过的常用读写操作；每种长任务有状态恢复/刷新语义，输出不含凭据；覆盖取消、失败、部分完成及重试的 manager/widget/API 契约测试。Web 专属能力明确记录，不默认为已迁移。

### Goal 4：迁移日志、配置与维护能力

按功能矩阵迁移日志浏览/过滤/详情、必要的实时或轮询刷新、配置读取和安全编辑、备份/恢复等管理功能。日志大结果要分页/限制和按需加载；高风险设置、删除、恢复等操作显示后端对象与影响范围，避免在本地缓存敏感值。

复用已有 FLS Release 最近 10 个版本、更新日志、版本切换和 APP 更新；复用 Python/Full 镜像、下载进度与镜像选择等本机容器管理，不重复造同名流程。后端缺少对应能力时记为后端子任务，先定义和验证 API 再开放 APP 写操作。

**验收：** 对照契约测读写与副作用；验证敏感字段脱敏、不在日志/崩溃信息中泄露；大列表保持有界加载；备份/恢复失败不误报成功。

### Goal 5：全域一致性、回退与默认入口切换

对全部迁移域做功能矩阵复核，修复交叉导航、服务器切换、过期页面状态、并发请求和认证过期问题。主导航按概览、任务、脚本、记录和管理分组，合集归任务域，避免每个新增 Web 菜单都占一个底部导航位。经用户确认原生实现覆盖完整且可用后，APP 默认主导航切到原生 UI；WebView 继续保留为显式备用入口。

**验收：** 全功能矩阵状态均为“APP 已覆盖且有验证”或有明确保留 Web 的原因；CI 格式/分析/单测/构建通过；真机使用、生命周期和 Android 网络/权限行为由用户手动验收，不使用 ADB 或模拟器作为开发门槛。

## 后端协作与工作边界

现有后端 API 不满足原生界面的正确性、批量效率、实时状态或安全要求时，拆成可单独验收的 FLS 后端任务：先定位路由/服务/权限和现有测试，在 FLS `develop` 补 API 契约与后端回归测试，再接 APP `develop`。需要直接推进后端时，可通过用户提供的 `.ssh` 远程脚本进入 FLS screen 会话开发和验证；只在隔离测试实例部署，不要只在 APP 加特判掩盖后端缺口。后端相关改动记录 FLS 分支/提交及测试结果，APP 记录对接的接口版本/提交。

前后端按小批次纵向交付：FLS `develop` 先确定字段、错误和测试 fixture，APP 可据此并行做页面与 manager 测试；正式接入以 FLS 已提交的契约为准，并保留 Web 原行为。每批记录 APP/FLS SHA、工作流与手动验收状态；待手动反馈不阻塞下一批方案与开发，但不能冒充已验收。不得用临时修改远端运行目录代替 Git；screen 只用于隔离实例联调。

## 持续验证和设备反馈

- 用户不需要提供 ADB 或模拟器测试；开发期间以 manager/widget/HTTP 契约测试和 GitHub Actions 为自动验证。
- APP Android CI 同时监听 `main` 与 `develop` 的 push/PR；APK Release 发布步骤仍仅限 `main`，因此可以在未合并阶段验证原生改动。
- 每个 Goal 按小批次实现，先写可复现测试，再实现，执行格式、静态分析、聚焦测试和全量 CI 构建。
- API 集成测试需要用户提供/选定的测试面板和非生产测试数据；没有真实服务可用时，明确标记集成未验证，不以 mock 测试冒充真实服务验收。
- 用户可在任一阶段手动验证并反馈。记录 APP/后端版本、面板模式、步骤、实际与预期、脱敏日志；将问题转成自动化回归测试后修复。
- 版本号、提交、推送和工作流验证按用户要求执行；CI 成功不等于真机/真实后端集成均通过。

## 后续 Goal 执行入口

继续开发时先读取本路线、功能矩阵和当前业务规格，核对两仓远端与工作区，再选择第一个尚未完成的批次。当前下一批是代理；新接口名称及字段以 FLS 已提交实现为准，不能把规格草案当成已有服务。代理完成后依次推进通知、备份恢复、首次设置与维护，再回到矩阵补齐任务/合集/日志及统一恢复入口，最后整理全域导航和视觉一致性。

每个批次的停止条件是可复核的纵向候选：后端契约及聚焦回归、APP 原生入口和主要异常流程、双方版本递增/提交/推送、工作流结论、APK 对应 SHA、未完成项和手动验收步骤。未执行或失败的检查明确保留；文档单独提交不改变 APK 的构建 SHA。未收到用户手动反馈可以继续下一域，但所有适用业务、双方 CI 和用户验收均满足前，整个 Goal 保持未完成且不合并 main。
