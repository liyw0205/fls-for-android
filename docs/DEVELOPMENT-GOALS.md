## 开发顺序

每一批都按“真实 Web 行为与服务实现 → FLS 契约/测试 → APP 原生页面/测试 → develop 配对验证”闭环交付。已有原生页面继续复用，按 [全量功能矩阵](FLS-FEATURE-MATRIX.md) 补缺；不重新开发已经通过验证的本机镜像、脚本安装或版本管理。

| 批次 | FLS 后端工作 | APP 原生工作 | 退出条件 |
| --- | --- | --- | --- |
| M1 代理诊断 | 显式异步启动、只读状态/历史、幂等与新尝试重试、有界检测 | 已保存/草稿检测、多选逐项结果、详情/历史/恢复 | 配置与全部诊断流程覆盖；GET 零探测；未知结果不重复执行 |
| M2a 通知配置 | 已实现 13 类渠道 schema/分页/局部写入、默认渠道、只写凭据及配置回执 | 已实现列表/表单/默认选择、启停/删除、冲突合并和原提交查询 | 自动化配对验证，手动验收待用户；保存绝不发送通知 |
| M2b 通知投递 | 待补异步发送、只读原请求查询、安全历史/正文及同一投递的显式重试 | 待补测试确认、投递历史/详情、原请求恢复及明确新尝试 | 与 M2a 配对覆盖通知全流程；响应丢失不自动重发，GET 不发送 |
| M3 备份恢复 | 列表/作业 DTO、下载、导入/恢复预检查与结果确认 | 创建/下载/删除、文件导入、范围确认、恢复/调度器恢复 | 备份与恢复可完整操作；失败/部分完成/未知状态可恢复 |
| M4 首次设置与维护 | 首次设置 JSON、面板版本/更新作业、控制与时间同步契约 | 首次设置、服务端更新/日志、重启/停止、时间同步 | 区分远程服务端维护、本机容器维护、APP 更新；断连不当作成功 |

| M6 全量导航与主题统一 | 按跨域流程补少量必要字段，保留 Web 兼容 | 完整原生面板导航、跨页流程、主题与交互统一 | 正常使用不依赖 WebView；窄屏/大字/横屏可用 |
| M7 配对验收与合并准备 | 完整后端回归、兼容性及隔离面板验证 | 完整 CI、最终 APK、用户手动验收反馈修复 | 功能矩阵逐项验收，形成一对确切 APP/FLS 候选提交 |

这些批次是实现顺序，不是新的自动 Goal 实例。当前总 Goal 持续推进到全量完成；任何单批完成都只更新该批状态。每批原生页随功能一起完善，M6 再核对全局一致性，避免把全部交互问题留到最后。

## M1：代理异步诊断候选已实现

FLS `1344fa5` / `20261126.8` 已实现 `POST /api/proxy/checks`、`GET /api/proxy/checks[/<id>]` 与显式 retry；17 项新增测试及相关回归共 116 项通过，三个打包工作流成功。APP `6ad8279` / `0.1.50+63` 已接单项/草稿/批量检测、结果/历史及重试；Android CI [45741020922](https://github.com/liyw0205/fls-for-android/actions/runs/45741020922) 已通过格式、分析、187 项测试和 arm64 APK 构建，[artifact 15081412300](https://github.com/liyw0205/fls-for-android/actions/runs/45741020922/artifacts/15081412300) 到期于 2026-12-10 02:19 UTC。实际契约和证据见 [代理规格](PANEL-PROXY-PLAN.md)。批量由 APP 按序提交、逐项持有 request/check ID，服务端最多同时执行 3 个作业并限制 12 个活动/等待项。M1 自动化候选验证已完成，M2a 配置进展见下节；M2b-M7 和真实面板手动验收仍待推进。

后端重点是先持久化再启动、相同 request ID 不重复探测、代理版本快照、草稿凭据仅留内存、重启后无法确认则 unknown。检查 requests 响应读取量及 Git 子进程输出上限，不直接持久化原始异常。历史白名单兼容旧记录；GET 不触发探测、重试或配置写入。线程启动失败、持久化失败、并发上限与响应丢失均需验证。

APP 在现有代理列表/表单加入连接与质量检测、草稿检测、多选结果、历史与单作业详情。普通 HTTP 显示状态码并区分可达与响应成功；GitHub 固定 raw/Git 目标按实际结果呈现。离开页面只停轮询，不显示没有后端支持的取消成功。手机测镜像源与远程 FLS 测代理分别展示，不能互相充当测试结果。

## M2：通知渠道与发送历史

M2a 已按 [通知迁移规格](PANEL-NOTIFY-PLAN.md) 实现并推送两个 develop：FLS `115f42a` / `20261126.9`，APP `efc61f9` / `0.1.51+64`。后端新增 18 项测试，连同通知操作/保存/测试/重试恢复和存储回归共 101 项通过，三个打包工作流成功。APP 已有 13 类渠道的 schema 表单、筛选/分页、局部编辑、默认渠道、启停/删除、冲突合并和未知保存结果只读恢复；最终 APK 证据见路线图。配置保存不触发测试发送，不能把该子批算作完整通知域完成。

从 FLS `routes/notify/`、`routes/api.py` 及 `test_notify_*_recovery.py` 核对渠道类型、字段规则、默认渠道和现有恢复语义。已有 `/api/notify/action`、`/test/<id>`、`/history`、`/retry/<id>` 不等于完整原生契约；逐项确认输入、错误白名单、状态查询与真实发送副作用后再复用。

M2a 的列表/详情/schema、逐凭据保持/替换/清空、默认版本及单项版本、任务引用保护、配置回执已实现。凭据不读回，未知配置提交 ID 仅保留在当前面板内存；跨 APP 进程恢复归 M5。代理和通知配置的真实面板手动验收可独立反馈，不阻塞接续开发。

下一步 M2b 先固定有界异步发送与只读查询契约，再接 APP 测试确认、投递历史/显式正文读取和重试。已有重试递增同一条投递的 attempt；测试通知不走任务分块，而任务每个分块分别落历史。failed 不证明接收方未受理，正文截断和部分发送必须明确显示，不能因超时自动重发。覆盖存储/线程启动失败、重启未知、当前渠道或投递版本变化、发送后断网和 401 恢复。开发测试注入 sender，不向真实接收人投递；具体实施及验收次序见通知规格。

## M3：备份、导入与恢复

复用 FLS `routes/backup/` 现有 create/job/cancel/list/delete、import、restore status/history、reload 和维护确认服务。先核对响应中路径/错误、上传及展开上限、恢复范围、互斥阶段和依赖安装行为；缺预检查或 JSON 下载契约时补 API，不让 APP 自行推断归档内容。

APP 通过 Android 文档选择器导入/导出，显示真实传输字节、服务端阶段和可取消边界。创建范围、删除对象、恢复影响和依赖安装须明确展示；已恢复数据但调度器重载失败时提供独立恢复操作。恢复导致会话失效或服务断开时，重新连接后查询原 request ID，不能再次提交归档。备份仍排除原生会话数据库及其 WAL/SHM/journal。

验证坏归档、超限、存储失败、并发备份/恢复、取消竞态、部分提交与重启恢复。远程恢复由远程 FLS 执行；不得把服务器目录映射到手机本机路径。

## M4：首次设置、版本与面板维护

首次设置目前在 `/setup` Web 路由，先定义初始化状态读取及 JSON 设置契约，再接 APP。初始化仅在未配置状态可用；已有面板继续原生登录/session/二次验证流程，不以初始化接口绕过认证。

面板维护以 FLS `routes/about/` 的 version/jobs/panel_control/time_sync 实现为准。补显式 POST 启动作业、只读状态/日志、可支持的平台能力和原请求查询；重启/停止只表示已受理时，APP 不把掉线视为操作完成。时间同步按服务端权限报告结果，不伪造无权限平台上的成功。

复用已有本机 FLS 最近 10 版/日志/切换与 APP 更新实现；新增的是远程及本机服务端面板维护的原生覆盖。开发候选不自动写入正式更新源；两个 develop 全量验收前不合并 main，不发正式 tag/Release。

## M5：补缺与跨进程恢复

按矩阵重新逐页对照 Web 表单与 JS 请求，优先确认合集复制/批量操作、任务剩余动作、日志单文件/分组删除、概览 RAM/磁盘和历史异常、脚本目录删除及其他尚未覆盖操作。这里是核对清单，不代表所有项都已确认需要新 API；发现 APP 不适用项须记录具体原因，不能只写“保留 Web”就算完成。

统一恢复记录只保存面板身份、操作类型、request/job ID 及必要时间；不保存草稿、密码、变量值或归档内容。记录须在提交可能产生副作用前保存，启动/重登后只查询原 ID，不自动重放。明确缺失记录、服务端保留期届满和未知结果，未经核对不得删除恢复记录或解锁重复写入。相同地址连接到被替换的实例时也不能误恢复旧操作。

覆盖配置/代理/变量、任务/合集、文件作业、通知和备份维护等域；后端没有只读原提交查询的域先补契约。处理面板切换、401 嵌套路由退出、旧请求回包、APP 进程退出和会话更新。保留期与清理规则在实现时固定并由测试验证。

## M6：APP 全量新前端

按 [原生面板导航](APP-RENDERING-PLAN.md#原生面板导航) 落地概览、任务、脚本、记录、管理；合集归任务，文件/在线脚本归脚本，管理聚合配置/代理/通知/备份/维护。APP 外层仍区分远程连接与本机环境，复用现有页面，逐步拆出 `PanelTasksView` 里的面板壳职责。

继续最初参考 [DeepSeek chat-demo](https://github.com/deepseek-ai/chat-demo) 的主题方向，按 FLS 管理工具的实际信息与移动操作实现；统一现有主题、表单、列表、状态、确认、日志和进度交互。主题参考不改变 FLS 的业务信息架构，也不能代替完整功能迁移。已有页面纳入同一轮视觉检查，不只美化新增页面。

验证跨页导航与返回、筛选/分页保留、服务器身份可见、长日志有界加载、键盘下表单操作、320/360 dp 窄屏、大字号及横屏。远程和本机使用同一业务页；日常流程全由 Flutter 完成。WebView 保留为用户明确选择的兼容入口，不作为未完成流程的验收证据。

## 每批验证与证据

1. 记录同步后的双方 SHA、当前版本、实际路由与字段；新增契约先写明副作用、错误与恢复语义。
2. FLS 执行与变更相关的 API/服务及旧 Web 恢复回归；APP 执行格式/analyze，并在 GitHub Actions 运行测试与 arm64 APK 构建。Termux 不支持 Flutter tester，不将未运行测试写成通过。
3. 实现批次递增对应仓库版本、提交并推送各自 develop，追踪工作流到终态并修复失败。仅文档变更不制造新版本或 APK；已有产物继续指向实际构建 SHA。
4. 回填矩阵与本计划的批次状态、配对 SHA、CI 链接、APK artifact/有效期、自动化边界和剩余缺口。用户手动验收待办单列，不做 ADB/模拟器测试。

本地 `$HOME/fls` 是当前可开发的后端工作区。需要远程运行验证时，可沿已授权的 SSH 远程脚本进入 FLS screen 开发会话；先确认是独立 develop 工作目录、端口和数据目录，再同步候选。不能仅凭会话名为 fls 就替换稳定面板；远程未实际执行的验证保持未执行。

## 最终完成与合并条件

M1-M6 全部实现并不自动满足发布条件。M7 必须以同一对 APP/FLS 提交核对矩阵全部适用流程、双方最终 CI、旧客户端/Web 兼容和用户手动验收反馈；有未完成项就继续开发并保持总 Goal active。未验收不阻塞其他批次开发，但两个 main 都不提前合并。

全部条件满足后整理可审查的合并候选和发布顺序：先兼容旧客户端的后端，再配套 APP。全量原生前端及用户验收完成前，不执行任一 develop 到 main 的合并或正式发布。
